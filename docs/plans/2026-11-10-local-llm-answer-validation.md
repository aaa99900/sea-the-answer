- 상태: 완료
- 품질 판정: 연결·평가 완료, 전반적 생성 품질 미달
- 작성: 2026-11-10
- 관련: [질문창 보완](2026-11-10-conversation-first-queries.md), [LLM 공급자 계약](../specs/llm-provider.md)

## 목표와 범위

실제 설치된 Qwen을 로컬 앱의 기존 Chat Completions 연결 경계에 연결해 원문 발췌 대체와 실제 모델 생성을 구분한다. 문서 질문의 한국어 의미·수치/단위/조건·정확한 인용·근거 부족·후속 범위 및 조회 도구와의 연결을 점검한다. 설치 모델과 자원부터 확인하며 운영/개인 DB·기존 설정을 덮어쓰거나 팀 서버에 배포하지 않는다.

## 단계

- [x] 설치된 모델·호스트/컨테이너 연결·자원 확인, 격리 앱 구성.
- [x] 고정 근거의 실제 생성과 API 검색+생성, 업무/후속 질문 평가.
- [x] 발견한 화면 호출 모드 보완과 관련 단위 검사. 생성 지시문 실험은 의미 오류가 남아 채택하지 않음.
- [x] Docker 전체 회귀와 실제 화면 확인 결과 확정.
- [x] 원래 답변·최종 답변·시간·생성/대체·의미 오류와 한계 기록, 실행 환경 정리/사용 방법 전달.

## 판정 원칙

`mode=llm`이나 `llmConfigured=true`만으로 생성 성공으로 보지 않는다. 실제 공급자 응답과 앱의 `generation`, fallback 경고·인용 검증 결과를 확인한다. 정확한 인용도 의미 정답을 보장하지 않으므로 질문별 기대 사실·조건을 원문과 대조한다. 이번 의미 검토는 Codex의 원문 대조이며 독립된 사람/전문가 검토가 아니다. 모델이 호출되지 않는 자료 현황/도구 계산을 모델 생성 성공에 합산하지 않는다. 로컬 모델 결과를 팀의 다른 배포 모델 품질로 일반화하지 않는다.

## 진행 기록

- 설치 모델은 Qwen2.5 3B/0.5B(Q4_K_M), RAM 15.7GiB, Intel Iris Xe이며 실제 Ollama 추론은 CPU다. 기존 모델 다운로드/교체 없이 loopback Ollama와 전용 Compose 앱을 연결했다. 실제 MRV 80,552행·DWT 후보 25,240행·AIS 307개를 격리 DB/읽기 전용 수집본으로 준비했다. 일별 앱 기록 3개는 명시적인 가상 시험 기록이다.
- 기존 지시문 16문항에서 형식상 답변 4, 빈 근거부족 3, 오류 9였다. 오류는 시간 초과 5/인용 등 검증 실패 4이며, 답변 4건도 의미 정답을 뜻하지 않는다. 짧은 지시문과 인용 enum 구조를 별도로 실험했다. 인용 선택 실험은 형식 통과를 늘렸지만 조건 누락·근거와 다른 단정이 남아 앱 생성 코드에는 채택하지 않았다. `api/llm.py`는 작업 시작 시 SHA256 `96adfb49bd62acf449604524ae0205daf6a3a5a610b631311ca3c3260a6c0379`로 복원했다. 중간 파일 이름의 production-final은 당시 실험 단계를 뜻하며 최종 채택본이 아니다.
- 비교 재현을 위해 기존 3B 가중치를 재사용한 로컬 alias `haedap-qwen3b-eval:20261110`만 만들고 온도 0·seed 42·context 4096을 지정했다. 가중치 다운로드와 기존 모델 변경은 없었다. 이 alias는 팀 배포 모델이 아니다.
- 화면 기본 모드가 원문 발췌이고 선택 UI가 없어 설정된 모델이 일반 질문에서 호출되지 않을 수 있음을 확인했다. 설정된 경우 실제 AI 모드를 기본으로 하고 원문 발췌 선택을 복구했다. 명시 선택은 현재 계정의 재연결에 보존한다. 관련 frontend 35개와 최종 생성/권한/질의 backend 관련 182개를 확인했다. 모델 실험의 시간은 cold/warm·시스템 부하가 섞인 관측값이며 공정한 성능 비교 수치로 사용하지 않는다.

## 최종 코드의 실제 앱 평가

핵심 15회 요청은 실제 로그인·CSRF·PostgreSQL·검색·계산·Ollama를 사용했고 모두 HTTP 200이었다. HTTP 성공을 답변 정답으로 집계하지 않는다. 모델 서버 앞의 임시 loopback 기록기는 본문을 변경하지 않고 실제 요청/응답만 기록했다. 앱/개인/팀의 운영 DB 대신 별도 Compose 프로젝트를 사용했다.

| 경로 | 관측 결과 | 판정 범위 |
|---|---|---|
| AIS 자료 유무 | 실제 수집본 307개/307척, 출처·노후화 안내 | 고정 도구 성공, 모델 생성 아님 |
| 가상 검증호 2025년 1월 → `2월은?` | 연료 5t → 4t, 각각 기록 2일/1일 및 기간 누락 표시 | 가상 기록의 조건·후속 재조회 확인 |
| 실제 YEOMAN BANK, IMO 7422881, 2022년 | DWT 후보 38,997t 연결, MRV 참고 탄소집약도 7.918235 | 공식 CII/등급은 null, 공개 제원 후보의 참고 계산 |
| 헬싱키 항구 참조 | 공개 자료·미확인 조건·오래된 자료 경고 | 실제 입항 승인 아님 |
| 황 함유량·CII 정의·GT/DWT·해리/노트 | 6개 일반 문서 질문 중 앞 4개: 약 28초 후 원문 발췌로 대체 | 모델 생성 실패 |
| 미래 부산항 날씨·공식 CII A등급을 만들라는 지시 | 나머지 2개도 시간 초과로 발췌 대체 | 모델의 올바른 거절로 집계하지 않음 |
| 선택 문서 기록 항목 | 25.7초 후 원문 발췌로 대체 | workflow 완료 표시여도 모델 생성 성공 아님 |
| 같은 문서의 장비 조작 절차 후속 | 19.7초, `실제 장비 조작에는 선박의 승인된 절차가 필요하다` + 정확한 인용 | 실제 모델 생성 확인; 근거는 가상 연료 전환 점검표 |
| 같은 문서의 선장 실명 | 8.5초, 실제 모델 `insufficient=true`, 이름 생성 없음 | 이 사례의 근거 부족 응답 확인 |

15회 요청 안의 실제 모델 호출 11회는 작업 선택 2회(`unknown`으로 규칙 대체), 생성 시간 초과 7회, 근거 있는 답변/근거 부족 응답 각 1회였다. 따라서 도구·조회 경로 확인과 일부 실제 생성은 성립하지만 **전반적인 자유 생성 품질 통과는 아니다**. 선택 문서를 고르라는 나머지 1회는 정상 되묻기이며 모델 호출이 없다.

별도 가상 연결 확인 문서의 짧은 질문 2회도 전체 문서 검색에서 다른 근거가 함께 들어가며 약 28초 후 발췌로 대체되었다. 이를 성공 사례로 포함하지 않는다. 실제 UI의 GT/DWT 질문도 모델 호출 시도 후 발췌 대체·실패 안내를 표시했다. 데스크톱/390px 화면을 확인했고 이 브라우저 흐름은 모델 품질 평가와 구분한다.

임시 기록기를 종료하고 Ollama에 직접 연결한 최종 재검사에서는 모델 사전 적재 요청만 52.8초가 걸렸다. 앞서 실제 모델이 근거 부족으로 답했던 같은 선장 이름 질문도 이번에는 34.4초(앱 전체) 후 `MODEL_FAILED_EXTRACTIVE_FALLBACK`으로 대체되었다. 두 번의 모델 응답 성공을 안정적인 동작으로 일반화할 수 없다. 이 1회는 위 15회 평가와 별도이며 `direct-final-smoke.json`에 보존했다. 사전 적재 시간과 API 질문 시간을 합쳐 모델 생성 시간으로 표기하지 않는다.

## 남은 품질 과제

- 실제 팀 배포 모델·GPU·검색 색인·동시 부하에서 같은 질문을 다시 평가해야 한다. 로컬 3B CPU 관측을 팀 서버 성능으로 간주하지 않는다.
- 현재 문서 생성의 모델 읽기 제한 25초와 전체 생성 예산 28초 안에 한국어 설명·근거 인용을 끝내지 못하는 사례가 많다. 제한을 늘리는 변경은 채택하지 않았다.
- 고정 근거 실험에서 질문의 필수 조건 누락·과도한 금지 단정·근거 부족 오판이 나왔다. 인용 형식만 강제해 해결됐다고 보고하지 않는다.
- 모델을 자동으로 다른 가중치로 전환하거나 새 모델을 다운로드하지 않았다. 새 의존성·migration·PR/push·팀 서버 배포도 없다.

## 회귀와 실행 환경 정리

- 최종 생성 코드를 복원한 상태의 관련 backend는 182개 통과, frontend는 35개와 production 빌드 통과다.
- 전체 PostgreSQL Docker 회귀는 33 passed / 1 failed(5.5분)였다. 추가한 답변 방식 선택으로 메뉴가 1개에서 2개가 되고 설정된 경우 요청이 `llm`이 된 점을 기존 `ui-conversations` 기대값에 반영했다. 첫 재검사에서 남은 요청 모드 기대값도 확인·수정했고 최종 해당 파일 2개 통과(24.3초)를 확인했다. 전체 34개를 수정 후 다시 실행했다고 기록하지 않는다. 실제 모델 브라우저 1개 통과는 대체 안내 표시 검증이며 생성 정답률이 아니다.
- 회귀 전용 `haedap-qwen-regression-20261110`만 `down`으로 정리했다. `-v`는 사용하지 않았다. 실제 모델 확인 앱은 다른 프로젝트 `haedap-qwen-live-20261110`이며 UI `http://127.0.0.1:5175/chat`, API `http://127.0.0.1:8003`을 사용한다. Ollama 주소는 `http://host.docker.internal:11434/v1`로 직접 연결했고 임시 요청 기록기는 종료했다.
- 실제 모델 확인 앱의 DB는 e2e tmpfs 기반 임시 DB다. 사용자 개인 DB나 팀 배포 DB가 아니며 컨테이너 재생성/종료 시 보존되지 않는다. 시험 스택을 실제 운영 방법으로 사용하지 않는다. 모델은 메모리에서 내려갈 수 있어 이후 첫 질문에 적재 시간이 추가될 수 있다.

## 로컬 증거 위치

`output/local-llm-20261110/`는 Git에서 제외한 시험 기록이다. `api-final.json`은 핵심 15회, `api-model-transport.jsonl`은 실제 공급자 요청/응답과 추가 확인, `live-ui.log`와 `browser-results/`는 실제 화면, `backend-final-focused.log`·`docker-regression.log`는 회귀 결과다. 원시 질문·문서와 가상 시험 계정 정보가 포함될 수 있으므로 전체 폴더를 공유/커밋하지 않는다. 자격증명은 프로젝트 문서에 복사하지 않는다.
